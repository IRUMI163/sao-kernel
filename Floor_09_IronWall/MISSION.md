## 1. この階層で学ぶC言語とUNIX哲学の核心

### ① なぜ標準出力（`stdout`）と標準エラー出力（`stderr`）を分離するのか？
UNIXシステムには、プロセスが標準で持つ3つのI/Oストリームが存在します。

| ストリーム名 | ファイル記述子 | C言語でのストリーム | 用途 |
| :--- | :--- | :--- | :--- |
| 標準入力 (`stdin`) | `0` | `stdin` | キーボードやパイプからのデータ入力 |
| 標準出力 (`stdout`) | `1` | `stdout` | プログラムの正常な実行結果・データの出力 |
| 標準エラー出力 (`stderr`) | `2` | `stderr` | エラーメッセージ、警告、ログの出力 |

#### 分離する最大の理由：パイプライン処理の保護
UNIX思想の根本には「1つのプログラムには1つのことを上手くやらせよ（Do One Thing and Do It Well）」という原則があります。複数のプログラムをパイプ（`|`）で繋ぐ際、`stdout` のみが次のプログラムへ受け渡されます。

もしエラーメッセージを `stdout` に出力してしまうと、後続のプログラムがエラー文字列を正常なデータと誤認して処理を開始し、システム全体に二次災害を引き起こしてしまいます。エラーメッセージを `stderr` に出力することで、パイプラインのデータを汚染せずにエラーを通知できます。

```text
[正常なデータ流路]
./floor_runner data.txt | grep "TARGET" -> (stdoutのみがパイプに渡る)

[stderr分離時]
./floor_runner invalid.txt 2> error.log | grep "TARGET"
-> stdoutはパイプへ、stderrはerror.logへ分離保存される
```

### ② `<errno.h>` と `strerror(errno)` / `perror`
C言語の標準ライブラリ関数（`fopen` や `stat` など）が失敗した際、システムはグローバル変数 `errno` にエラー番号（整数）をセットします。

- **`errno`**: 直前に実行されたシステムコール/標準ライブラリのエラー番号（例: `ENOENT` = 2, `EACCES` = 13）。
- **`strerror(errno)`**: エラー番号に対応する人間が読める文字列メッセージ（例: `"No such file or directory"`, `"Permission denied"`）を返す関数（`<string.h>` に定義）。
- **`fprintf(stderr, ...)`**: `stderr` に対して書式設定付きで出力する関数。

```c
#include <stdio.h>
#include <string.h>
#include <errno.h>

FILE *fp = fopen("missing.txt", "r");
if (fp == NULL) {
    // stderrにエラーメッセージを出力
    fprintf(stderr, "[IO ERROR] %s\n", strerror(errno));
    return 2;
}
```

### ③ 終了ステータス規約（Exit Status）
プロセスが終了するとき、OSに返却する数値（`0`〜`255`）を終了ステータス（Exit Status / Return Code）と呼びます。シェルスクリプトや後続プロセスは `$?` を参照して結果を判定します。

| 終了コード | 意味 | 本階層での割り当て |
| :--- | :--- | :--- |
| `0` | 成功（SUCCESS） | ファイル読み込み＆行数カウント成功 |
| `1` | 汎用エラー / 引数エラー（USAGE ERROR） | コマンドライン引数が足りない場合 |
| `2` | I/O・環境エラー（IO ERROR） | ファイル非存在、権限不足、ディレクトリ指定など |

---

### ④ UNIXパイプラインとリダイレクト
シェルコマンドにおける出力の制御記号をマスターしましょう。

- `>` : `stdout` をファイルへ上書き保存（例: `./app > out.txt`）
- `2>` : `stderr` をファイルへ上書き保存（例: `./app 2> err.txt`）
- `2>&1` : `stderr` を `stdout` と同じ出力先に統合
- `|` : 前のコマンドの `stdout` を次のコマンドの `stdin` に流し込む

### ⑤ Gitのブランチ・Pull Request運用
大規模開発や parallel AI 開発では、メインブランチ（`main`）に直接変更を加えることは固く禁じられています。

1. **ブランチ切替**: 機能追加やバグ修正ごとに `feature/floor-09` などの独立したブランチを作成して作業する。
2. **コンフリクト防止**: 担当外のディレクトリや共有ファイル（`Makefile` や `AGENTS.md` など）を変更しない。
3. **Pull Request (PR)**: 作業完了後、テストを通過したコードのみを PR として提出し、自動CIテストおよびコードレビューを経てマージする。

## 2. 現場で飛び交う業界用語辞典

- **`stdout` / `stderr`**:
  標準出力と標準エラー出力。画面上に一見同じように表示されていても、内部の出力ストリーム（ファイル記述子 1 と 2）として完全に区別されている。
- **`errno`（Error Number）**:
  システムコールやC標準関数が失敗した原因を示すスレッドローカルなグローバル変数。直後の関数呼出で上書きされる前に確認・保持する必要がある。
- **終了ステータス（Exit Status / Return Code）**:
  プログラムが OS や親プロセスに報告する状態コード。UNIXでは `0` が成功、非ゼロが異常終了を意味する。
- **パイプライン（Pipeline `|`）**:
  コマンドの出力を別のコマンドの入力へ直結するメカニズム。UNIXの強力な単機能ツール連携を支える基盤。
- **Pull Request（PR）**:
  自身のブランチで行った変更を本線（`main`）に取り込むよう依頼する Git の仕組み。

## 3. ボス戦ミッション（実装仕様）

本階層の課題プログラム `main.c` は、指定されたファイルの行数をカウントして出力するツールである。
受講者は異常系エラーハンドリングを完璧に実装し、堅牢なプログラムを完成させよ。

### プログラムの仕様
コマンドライン引数としてファイルパスを1つ受け取り、そのファイルの行数を計測して出力する。

#### 1. 正常系仕様
- ファイルを正常に読み込み、行数（改行文字 `\n` の個数、あるいは最終行）をカウントし、`stdout` に以下の形式で出力して終了コード `0` で終了する。
  ```text
  LINES: <行数>
  ```

#### 2. 異常系仕様（判定順序とエラーメッセージ・終了コード）
エラー発生時は **必ず `stderr` に** エラーメッセージを出力し、指定の終了コードで終了せよ（`stdout` には一切出力してはならない）。

1. **引数不足（USAGE ERROR）**:
   - 条件: 引数が指定されていない場合 (`argc < 2`)
   - `stderr` 出力: `[USAGE ERROR] File path required\n`
   - 終了コード: `1`

2. **ディレクトリ指定エラー（IO ERROR）**:
   - 条件: 指定されたパスがディレクトリである場合 (`stat` 関数と `S_ISDIR` マクロで判定)
   - `stderr` 出力: `[IO ERROR] Target is a directory\n`
   - 終了コード: `2`

3. **ファイルオープンエラー（IO ERROR）**:
   - 条件: ファイルが存在しない、または読み取り権限がない場合 (`fopen(path, "r") == NULL`)
   - `stderr` 出力: `[IO ERROR] <strerror(errno)>\n`
   - 終了コード: `2`
